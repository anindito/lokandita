# Decisions

Technical choices made during the build, newest first. One line each: date, decision, reason.

- 2026-11-23 — Stage 13, TS-PY: an import is run only when no student has submitted for ten minutes — the importer's `VALIDATE` jobs share the normal judge queue with students' jobs, and the meeting 2 import made 19 submissions wait 1 to 5 minutes.
- 2026-11-23 — Stage 13, TS-PY meeting 3: generators never produce a fractional result exactly on a class limit, and use the test index so that every branch appears among the 12 tests — at a limit the binary fraction depends on the order of operations, and random inputs alone often miss a branch.
- 2026-11-23 — Stage 13, TS-PY: from meeting 2 on a fractional result is printed with the number of decimals the statement gives and compared as text (`trimmed`), and the generator rejects any input whose result lies within 0.002 of a rounding boundary of the last printed decimal (or within 0.001 of a whole number where the answer is rounded up) — formatting is what the meeting teaches, and without that margin two correct orders of operations could print different last digits.
- 2026-11-23 — Stage 13, TS-PY: judge checks and imports were run on the evening of 2026-11-23 while students were working, on the owner's order; they run at low CPU priority (`nice -n 15`) and the agent reads the students' submission-to-verdict time before, during and after, and stops the check if it passes one minute.
- 2026-11-23 — Exam meetings: the strictness lives in `Ruang::mode` / `Ruang::jenis` and in one visibility rule (`Latihan::sqlNilaiTampak`, `Ruang::nilaiTampak`), not in the window columns — a pengajar can still edit `late_policy` or `post_close_visibility` rows through old forms or a crafted request, and an exam must not depend on nobody doing so.
- 2026-11-23 — Exam meetings: points stay the fixed points per level (3/5/8/10/15); there is no per-problem weight — the exam score is a percentage of the total, and custom weights would need a schema change and a second scoring path.
- 2026-11-23 — Exam meetings: after release a student sees points per problem number, not per title, and the own-data export names exam problems `soal-<id>` — the owner wants exam problems hidden after close, and a title or slug in a list is a way back to them.
- 2026-11-23 — Exam meetings: pressing "Buka selama N menit" again starts a new period from that moment — it is the lecturer's way to give extra time after an outage; the audit row records the old and new times.
- 2026-11-23 — Exam meetings: `GET /api/executions/{id}` keeps `progress` (queued / compiling / running test k of n) for a hidden exam submission and drops only `result` — progress carries no pass or fail, and without it the student sees a frozen page while waiting.
- 2026-11-23 — Stage 13, TS-PY: meetings 6–16 carry no concepts — concepts are inherited from every lower-numbered meeting whether it is used or not, so anything left on meeting 6 or 7 would be allowed in the mid-term at meeting 8; the layout was changed by one audited SQL transaction with the owner's approval because `benih:kurikulum` only fills empty rows and retitles.
- 2026-11-23 — Stage 13, TS-PY: before `FORMAT_OUTPUT` is allowed (meeting 1) a fractional result is printed as Python prints it and compared in `float` mode; inputs are whole numbers and the reference divides once, at the end — rounding or formatting would need a concept the meeting does not allow, and a single final division keeps the sample outputs readable (`0.6`, not `0.6000000000000001`).
- 2026-11-23 — Stage 13, TS-PY: meeting 1 reads one value per line, and every statement tells students to call `input()` without a prompt — first-week students know `input()` and `int(input())` only, and a prompt text lands in the judged output.
- 2026-11-23 — Stage 13, TS-PY: the separate calculation in `cek-ts-py-pertemuan-<n>.py` is also Python (the course language), so it is written by another route: exact fractions converted to metres first, `math.ceil`, `datetime`, and loops that simulate "how many fit" — the same formula typed twice would prove nothing.
- 2026-11-23 — Stage 13, TS-PY: rounding up without `if` is given in the statement as `(a + b - 1) // b` wherever a meeting 1 problem needs it — branching arrives at meeting 3 and `math` at meeting 2.
- 2026-11-23 — Stage 13: `docs/soal/periksa.py` checks a problem file before import in the same judge containers as the importer (the judge's own `soal.validasi`, then the reference output against the separate Python calculations and the quoted examples in `cek-<course>-pertemuan-<n>.py`) — the earlier meetings were checked with throw-away scripts, and eleven meetings need the check to be repeatable and committed.
- 2026-11-23 — Stage 13: statements use lists, not Markdown tables — the statement renderer is plain CommonMark (`Soal\Pernyataan`), which shows a table as lines of `|`; changing the renderer is app code and outside problem production.
- 2026-11-23 — Stage 13: generators use `INDEX` to force every branch and boundary value into each student's twelve tests, and small one-number inputs take the two sample tests from different halves of the range — otherwise a student could get two identical samples or never meet a boundary.
- 2026-11-23 — Stage 13: review sheets are files, `docs/soal/tinjauan/<course>-pertemuan-<n>.md`, generated from the import file by `docs/soal/lembar-tinjauan.py` (count per level, every title, full Indonesian statement of the first and last problem of each level) — eleven sheets do not fit in a chat message and the owner reads diffs in VS Code.
- 2026-11-23 — Stage 13, owner's decisions ("approve all"): PBO301 detection rules accepted as documented; `required_concepts_in_submission` is `CLASS_OBJECT` at meeting 2, plus `CONSTRUCTOR_DESTRUCTOR` at 3 (and `COPY_SEMANTICS` on the copy problems), `ENCAPSULATION` at 4, `KOMPOSISI_AGREGASI` at 5, `INHERITANCE` at 6, `INHERITANCE` and `POLYMORPHISM` at 7; DDP101 recursion problems require `REKURSI`; history of C++ and toolchain setup are not covered in PBO301 meeting 1; DDP101 meeting 6 stays without `REFERENSI` unless the owner ticks it, so the reference solutions of meetings 6 and 7 use no reference variables.
- 2026-11-20 — The source files turned out to be three (`import-mahasiswa.csv` with course and class per row, `import-dosen.csv`, `penugasan-pengajar.csv`), so there is no separate enrollment file: `data:pendaftaran` reads the student file, and `akun:impor` ignores its two extra columns.
- 2026-11-20 — The count check lives in LokaKode (`data:cocokkan`) and counts accounts through the `identity_reader` views — one command sees accounts and enrollments together, and LokaKode needs no new right for it.
- 2026-11-20 — The count check also fails on anything in the database that is **not** in the files (an active mahasiswa or dosen, an `AKTIF` enrollment, an assignment, a non-archived class of the active year) — "counts match" must mean both directions, otherwise leftover test rows pass unnoticed.
- 2026-11-20 — One bad row refuses a whole import (accounts, assignments, enrollments) instead of importing the good rows as the web pages do — the gate is equality with the file, and a partial import is harder to reason about than a corrected file.
- 2026-11-20 — `Pendaftaran::jalankan` passes its actor to the audit log explicitly and takes an optional `lewat` — it could not run outside a web request before; behaviour on the web is unchanged.
- 2026-11-20 — Seed titles of DDP101 meetings 2, 4, 5, 7, 8, 9 are the ones already typed in production, and UTS / UAS are written out for DDP101 and PBO301 — the owner had replaced the concept-code titles himself and his wording reads better than the map's; the seed then touches no existing title.

- 2026-11-19 — Owner's decisions for stage 9b (plan approved "approve all"): an optional `late_until` per class window, empty = late submissions accepted until the pengajar closes by hand, and a manual "open" is not late; practice-after-close submissions are judged and shown but never touch score, attempts, leaderboard or analytics, and practice keeps problems visible even with `hidden`; students see number and title of every practice meeting of their own course with the reason it is unavailable; the students' leaderboard is live, shows names without nomor induk, and when anonymised shows the others as "Peserta n"; at risk = no submission in a closed meeting, or a score below 50 in two or more meetings; exports are one row per student with one score column per meeting plus a detail sheet. Retention of `judge_jobs` / `imports`, problem-bank access for a pengajar, Monaco in the edit form and a memory limit per problem are not in this stage.
- 2026-11-19 — A student page for a meeting that is not published or not opened for their class answers 200 with the reason, like the existing "not open yet" state; this replaces the 404 for an unpublished meeting of 2026-11-17 below — owner's instruction. A meeting of another course, a meeting not used for practice, and every problem of an unavailable meeting keep the 404 that equals a missing one.
- 2026-11-19 — What a student may submit now is one value next to `mode`: `Ruang::jenis` = `biasa`, `telat`, `latihan` or nothing. `mode` stays `kerja` for all three, so every existing check keeps working and only the scoring and the banners look at `jenis`.
- 2026-11-19 — A late submission stores the factor that applied when it was created (`submissions.late_factor`) — scores are recomputed in full from `submissions`, so a pengajar changing the window's factor afterwards must not silently change marks already given.
- 2026-11-19 — Distribution, mean, median and class comparison count every `AKTIF` student, with 0 for a student who has no judged submission, and show the number of non-submitters next to them — that is the grade those students have; leaving them out would make a class where half did nothing look good. The standard deviation is the population one (the class is the whole population, not a sample). The owner can overrule either.
- 2026-11-19 — Calibration thresholds (`Analitik::TERLALU_SULIT`, `TERLALU_MUDAH`): a problem "looks harder than its label" below a full-score rate of 50 % (mudah sekali), 30 % (mudah), 20 % (mudah-sedang), 10 % (sedang); "looks easier" above 90 % for sedang and sulit; no hint before 5 students attempted. Only the 30 % for `MUDAH` comes from `SPEC.md` §8.4; the rest are my numbers for the owner to change.
- 2026-11-19 — "Median time" of `SPEC.md` §8.4 is shown as the median CPU time of the students' best submissions (slowest test) — the system does not measure how long a student worked on a problem, and inventing it from timestamps would be a guess presented as a measurement. Labelled "median waktu jalan".
- 2026-11-19 — Leaderboards and class comparison for a course are scoped to the active academic year; a class board is scoped by the class itself.
- 2026-11-19 — The leaderboard cache holds only user ids and numbers; names are read from LokaAuth's directory on every request, and the staff or student shape is made after the cache — a cached board can therefore never leak a name to someone who should see "Peserta n".
- 2026-11-19 — Exports include `AKTIF` and `LULUS` students with a status column (withdrawn students are left out); an empty score cell means "no judged submission", not 0, so a lecturer can tell the two apart; numbers are numeric cells, everything else is text; every download writes `nilai.diekspor` to the audit log.
- 2026-11-19 — Chart.js 4.6.1 (MIT) comes from the npm registry tarball in a build stage, pinned by sha256 (its sha1 and sha512 equal the registry's), one minified UMD file, only into the LokaKode image. Charts are drawn from the HTML table on the same page, so the numbers exist once and the page is complete without JavaScript.
- 2026-11-19 — PhpSpreadsheet 5.11.0 added to LokaKode (the version LokaAuth already uses); `composer.lock` was updated inside the pinned Composer container.
- 2026-11-19 — "Back" arrows are a CSS pseudo-element (`.panah-balik`) that points right on right-to-left pages, in all three apps.
- 2026-11-19 — A compile that reaches the 10 s limit is a `CE` / `timeout` only when its container used at least 8 s of CPU; with less (or when it was stopped from outside before reporting) it is an infrastructure failure that the worker retries, ending at worst as `judge_unavailable`, which is not an attempt — owner's instruction for 9b; this replaces the sentence "a student's own compile timeout stays a `CE`" in the 2026-11-17 entry below. Measured on this server: the acceptance program uses 10,023–10,033 ms of CPU in 10 s with a whole CPU, and 9,044 / 7,082 / 5,103 / 3,046 ms when its container is throttled to 0.9 / 0.7 / 0.5 / 0.3 CPU, so 8 s separates "the source is heavy" from "the server was busy" with room on both sides. The same rule covers the reference solution in `VALIDATE`.
- 2026-11-19 — `pelari` also reports `cg_cpu_ms`, the CPU of the whole container from cgroup `cpu.stat` — `wait4` only counts children that were reaped, and when the wall-clock limit kills a compile, `cc1` dies before `gcc` reaps it, so the old figure could be near zero for a compile that had worked the whole time. Reading one more file in the container's own cgroup changes no limit. The judge image tag changes with it.
- 2026-11-19 — The CPU share of a judge container is the constant `kotak.CPU_KONTAINER` (`"1"`, as `SPEC.md` §10) so that tests can lower it to 0.3 and starve a real compile in a real container; nothing raises it.
- 2026-11-19 — The two load-sensitive isolation tests keep their limits (8 s for `while(1)`, 4 s for the orphaned child) but apply them to the run alone instead of compile + run, and additionally assert what `pelari` measured inside the container (CPU at the 2 s limit and wall-clock within 5 s; the orphan's run over in under 1 s) — the old measurement included the compiler and a second container start, which is what crossed the limit under load, not the thing the tests are about. Five repeats with four CPU burners running (load average above 6) passed.

- 2026-11-17 — Problems with a fractional answer use comparison mode `float` and inputs chosen so that the answer has at most six significant digits — `FORMAT_OUTPUT` is not allowed at meeting 2, so the reference prints with `cout`'s default precision, and an answer like 33.3333… would make the expected output itself a rounded number.
- 2026-11-17 — Before importing, every problem was checked twice outside the database: `soal.validasi` in judge containers (the same code as a `VALIDATE` job) and a comparison of the reference solution's output with an independent Python calculation on 36 generated tests — validation alone only proves that solution and generator agree with each other, not with the statement.
- 2026-11-17 — `kotak._buang` returns only when the container is gone (it retries while Docker answers "removal already in progress", for at most about 10 s) — two overlapping removals let the sandbox return while its container still existed, which the "no container left" check caught twice.
- 2026-11-17 — The two wall-clock limits in the isolation tests that were missed by a hair under load (8 s for `while(1)`, 4 s for the orphaned child) were not widened — a looser limit to get a green run would be the kind of test that passes for the wrong reason; the flakiness is recorded in `PROGRESS.md` instead, for the owner to decide.
- 2026-11-17 — `tahap-9a` is tagged after the owner's check, as with every earlier stage, not at the end of the agent's work as the plan said.
- 2026-11-17 — During `GENERATE`, a reference solution whose compile runs out of time or memory is an infrastructure failure (retried twice by the worker), not `generation_failed` — the version is approved, so it compiled at validation; in the 1,200-job measurement one such compile failed under load and its job stayed failed for good. A reference solution that the compiler refuses is still `generation_failed`. A student's own compile timeout stays a `CE` with reason `timeout`, as the stage 7 acceptance test requires.
- 2026-11-17 — The full-class measurement lives in `apps/lokakode/ukur/` and is run on purpose (`infra/tes.sh lokakode ukur/PraBangkitTest.php`), not with the suite — it loads the server for half an hour.
- 2026-11-17 — Measured in headless Chromium 158: with `style-src 'self'` Monaco raises one `style-src-elem` and dozens of `style-src-attr` violations, so the problem page keeps `style-src 'self' 'unsafe-inline'`; nothing else is relaxed. Monaco's default worker comes from a `blob:` URL, which `script-src` refused (the editor then ran its worker code on the main thread and threw an error event); instead of allowing `blob:`, `MonacoEnvironment.getWorkerUrl` points at `/js/monaco-pekerja.js`, six lines served from our own host. With both, the page loads with zero CSP violations and zero script errors, and every resource comes from the app's own origin (asserted by a test).
- 2026-11-17 — Browser tests drive Chromium through a 300-line DevTools Protocol client of our own (`tests/_support/Peramban.php`: WebSocket framing, `Runtime.evaluate`, real key and mouse input) instead of a Composer library — no new dependency or lock-file change for test-only code, and the handful of commands used is readable in one file.
- 2026-11-17 — The "paste is blocked" test is paired with a test in which a `paste_allowed` user presses the same keys and the clipboard text does arrive in the editor — otherwise "nothing was pasted" could also mean the test harness cannot paste at all.
- 2026-11-17 — The browser image `chromedp/headless-shell` is pinned by digest in `infra/tes.sh` (Chromium 158.0.8127.37, about 550 MB on disk); it is used only by tests and is never part of a deployed image.
- 2026-11-17 — Found in stage 9a: `Lokandita\Auth\Testing\Http` returns itself, so the stage 6 test "a forbidden class and a missing class get the same answer" compared one object with itself and proved nothing. It now copies the first body before the second request and compares the two pages without their CSRF tokens and the requested path (`KodeCase::inti`); the property holds. The other tests were searched for the same pattern; `EksekusiTest` uses two different clients and was sound.
- 2026-11-17 — What a student may do is one value, `mode` (`App\Libraries\Ruang::mode`): `tunggu`, `kerja`, `baca`, `nilai` — computed from the window, the enrollment status and the academic year in one place, and every student route asks only for that. An archived year never accepts a submission, whatever the window says.
- 2026-11-17 — Student routes answer 404 for anything outside the student's own enrollment (another class, another course, a meeting that is not published, a closed-and-hidden meeting), with the same page as a number that does not exist; "open but not allowed to submit" answers 403 `tertutup`.
- 2026-11-17 — A student keeps the version their instance was made from; a version approved later reaches only students without an instance — `SPEC.md` §8.2 (re-opening never regenerates) and §8.1 (old scores stay tied to the old version).
- 2026-11-17 — Rate limits (Run 3 s per student, Submit 10 s per student per problem) are Redis keys with `SET NX PX`; if Redis cannot be reached the request goes on and is logged. A second guard that does not depend on Redis sits in MySQL: at most one submission being judged per problem, at most two unfinished Runs per student.
- 2026-11-17 — A Run or Submit also saves the code as the draft — the code a student last ran is what they expect to find after a crash.
- 2026-11-17 — The problem page gets its data (template, draft, texts) from a `<script type="application/json">` block and all behaviour from `/js/soal.js`; there is no inline script, and everything that comes from a user or a program is written with `textContent`.
- 2026-11-17 — Monaco 0.52.2 (MIT) comes from the npm registry tarball in a build stage, pinned by sha256 (its sha1 equals the registry's `shasum`), only the `min` AMD build, only into the LokaKode image — the same pattern as Tailwind: no Node, nothing on the host, no CDN.
- 2026-11-17 — Only the problem page sends `style-src 'self' 'unsafe-inline'` (`SecurityHeaders::izinkanGayaSebaris()`), because Monaco creates `<style>` elements; `script-src` is unchanged everywhere. Whether Monaco needs more than this is measured in a real browser in step 7.
- 2026-11-17 — If Monaco fails to load, the page falls back to a plain textarea with the same paste blocking, autosave, Run and Submit — a student must be able to work even when a 3 MB script does not arrive.
- 2026-11-17 — Right-clicking in the editor only suppresses the menu; it shows no message and records no integrity event — opening a menu is not a paste attempt. The recorded paths are `paste`, `keyboard`, `shift_insert`, `middle_click`, `drop`.
- 2026-11-17 — Numbers shown to students use a dot and at most two decimals without trailing zeros (`angka()`), the same in PHP and in the page script, in all three languages.
- 2026-11-17 — The worker only reports a `SUBMIT` result in `judge_jobs`; the web app copies it into `submissions` and computes scores, in the request that polls the job and again whenever scores are read — scoring exists once, in PHP, and the worker needs no right on any new table; a closed browser tab loses nothing because the next reader finishes the work.
- 2026-11-17 — `problem_scores` and `meeting_scores` are derived tables, always recomputed in full for one student and one meeting from `submissions` — the "4 best very-easy problems" must be re-selected on every submission anyway (`SPEC.md` §7), and a full recompute cannot drift.
- 2026-11-17 — A window row carries `course_id`, tied to both the meeting and the class by composite foreign keys — MySQL itself refuses a window for a class of another course, as with enrollments in stage 6.
- 2026-11-17 — Minimum composition is five plain columns on `meetings`, not JSON — five numbers that are validated and compared one by one.
- 2026-11-17 — If the concept analysis of a student's source fails, the verdict stays `AC` and the result says `analysis_failed` — a failure of our parser must not halve a student's score.

- 2026-11-17 — Statements are rendered by league/commonmark 2.10 with `html_input = escape` and unsafe links removed; `{{param}}` is substituted before rendering — the file comes from an upload and is treated as untrusted input.
- 2026-11-17 — Code fields of the edit form are plain `<textarea>`; Monaco arrives with the student interface in stage 9.
- 2026-11-17 — PHP's `upload_max_filesize` is 9 MB and `post_max_size` 10 MB in the app image (all three apps) — the default 2 MB would have refused files `SPEC.md` §8.3 allows; tested with a 3 MB upload.
- 2026-11-17 — A refused problem is a `VALIDATE` result (`DONE`, `ok: false`), not a failed job, and reasons carry a code and positions while the sentence comes from the web app's language files — a verdict is never retried, and all user-facing text stays in `id`/`en`/`ar`.

- 2026-11-17 — Determinism is checked by running the generator three times for the first 3 of the 20 seeds, in three separate containers — "same `SEED`/`INDEX` three times" as `SPEC.md` §8.3 says, without tripling the cost of all 20 seeds.
